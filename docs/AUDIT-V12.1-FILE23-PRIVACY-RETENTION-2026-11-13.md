## A — Integrity and fail-closed retention/privacy

**V12.1-RETENTION-PROOF-01 (source defect):** `SPDB_Operations_Repository::cleanup_retention()` had nullable default `export_cutoff` / `export_max_id` and a SQL branch that deleted all expired export-job rows without the frozen upper row fence. The current background job normally supplied both, but this public repository method itself did not enforce the File23 metadata-first safety invariant. **Patch:** reject either missing proof field with `spdb_retention_proof_required`; remove unrestricted SQL DELETE branch. `tests/v12-1-retention-proof-boundary-tests.php` exercises absent, malformed, future and negative boundaries (9 assertions). This stops accidental direct/default metadata erasure but does not attest that Hostinger ran the associated filesystem cleanup.

**V12.1-INSTITUTIONAL-PRIVACY-02 (source defect):** `privacy_erase()` used `LIMIT 5000` when scanning institutional collection owner/contributor references, yet reported completed after processing the first 5,000. Malformed contributor JSON could be rewritten as an empty array, silently discarding unrelated contributors. **Patch:** strict integer contributor-list JSON validation, keyset pagination by collection `id` across bounded 200-row pages, skip `LIKE` false positives, preserve non-target contributors, fail closed on SQL/malformed order, reject truncated >20,000 records with explicit error. The parent `atomic()` rolls back the database transaction on such errors. `tests/v12-1-institutional-privacy-pagination-tests.php` covers 5,001 rows, user 7 vs 17, bad JSON and read/update errors (11 assertions). **Residual:** large-scale 20k+ operational continuation/recovery still requires a carefully authorized staging design; a deliberately bounded fail-closed status is not equivalent to a completed erasure.

## B — Scale, portability and accidental disclosure

**V12.1-OWN-COLLECTION-SCALE-03 (source defect):** owner erasure materialized all own collection IDs into PHP and then built an unbounded SQL `IN(...)` placeholder list for item removal. This could exceed SQL packet/parameter or PHP memory constraints. **Patch:** one scoped multi-table `DELETE item_rows ... INNER JOIN own_col` with the exact `scope='own'` and owner predicate, strict local schema identifiers, and parent InnoDB transaction. No File00/02/CF04 native content is deleted. `tests/v12-1-owned-collection-erasure-tests.php` (11 assertions) checks owner bind, scope, query shape, error propagation and no unbounded PHP list. True SQL/transaction behavior must be rehearsed on staging MySQL/MariaDB.

**V12.1-PORTABILITY-PAGING-04 (source defect):** WordPress personal export `privacy_collection_export()` previously exported at most 5,000 item pointers for each page's selected parent collections, so a single 6,001-item collection could silently omit subsequent items. **Patch:** independently page selected item pointers across globally ordered item IDs via a collection join, filter exact contributor membership after the broad SQL prefilter, strip internal parent permission fields before serialization, and keep `has_more` true whenever a candidate page is full. `tests/v12-1-privacy-collection-export-pagination-tests.php` exercises 6,001 owned items and user7-vs-17 false-positive candidates, with 6,128 assertions. **Residual:** per-page OFFSET behavior on concurrent item updates, anonymization scope, and large DB execution times require actual staging acceptance.

**V12.1-PORTABILITY-READ-05 (source defect):** multiple DB `get_results()` errors were being coerced to empty arrays so a partial WordPress privacy-data export could be reported as complete. **Patch:** return typed `WP_Error` for failed tasks/saved views/delegations/rules/export jobs/collections/items/knowledge link reads; propagate that error through `SPDB_Privacy_Integration::export_personal_data()`. WordPress core `wp_ajax_wp_privacy_export_personal_data()` handles `WP_Error` as an Ajax failure, preserving `data/done` shape for successful callbacks. `tests/v12-1-privacy-export-db-failure-tests.php` uses eight failing read routes and a valid empty DB (17 assertions). **Residual:** preferences `get_row()` still treats null as absent without independent SQL error distinction; real provider and core Ajax integration need staging observation.

## 13 November follow-up — Collections drift and preferences export

**V12.1-COLLECTIONS-SCHEMA-DRIFT-06:** `SPDB_Collections_Schema::maybe_upgrade()` would call `install()` after a same-version `verify()` failure (for missing tables, columns, indexes), so merely loading `admin_init` could trigger dbDelta/ALTER before a live-state freeze. **Source correction:** when the recorded option equals Collections Schema VERSION `4`, failed structural verification returns `spdb_collections_schema_drift` (with original cause code) rather than running automatic repair. New install/version-change path remains separate. `tests/v12-1-collections-schema-drift-tests.php` validates missing-table drift, zero DB writes and preserved recorded version (4 assertions). Real unversioned/partially deployed schema, type-level drift and Hostinger migrations still require operator inspection.

**V12.1-PREFERENCES-EXPORT-07:** `SPDB_Operations_Repository::get_preferences()` deliberately returns default preferences when no row exists, but could also hide an actual failed SQL SELECT. Its WordPress privacy portability caller now checks `$wpdb->last_error` after the preferences query and returns `spdb_privacy_preferences_read_failed` rather than claiming data export complete. The standard UI missing-row contract stays unchanged. `tests/v12-1-privacy-export-db-failure-tests.php` adds two assertions for the repository result and WordPress callback (19 in that suite). Real WordPress SQL behavior still requires staging QA.
