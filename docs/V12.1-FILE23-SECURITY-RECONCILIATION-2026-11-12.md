## Source defect ledger — V12.1-GUARD-01

**Finding (confirmed in the frozen repository source):** `private_directory()` created three web-server protection files if absent, but accepted any existing files without validating their type/content. A tampered pre-existing `.htaccess`, `index.php` or `web.config` could therefore be silently treated as acceptable by File 23. This is a **source-level defense-in-depth defect**; whether it existed on a deployed host has not been checked.

**Root cause:** presence-only check (`file_exists`) followed by unconditional acceptance.

**Change in this child branch:** preserve the existing server guard bytes for compatibility with existing matching installations, refuse symlinked/unreadable/non-regular/mismatched guard files and fail closed. Absent files continue to be created before validation. The export's encryption, per-owner HMAC and current File 00 authorization are unchanged.

**Regression:** `tests/v12-1-export-guard-integrity-tests.php` executes the actual private-directory method against a temporary uploads root and checks a fresh directory, a legitimate repeat read, tampered Apache/LiteSpeed and IIS guards, missing guard recreation and symlink refusal.

**Acceptance:** exact child-head PHP 8.0–8.3 syntax/tests/architecture/companion CI green, two independent post-change reviews and Hostinger staging tests. Until all are independently evidenced, classify as **source patch pending acceptance**, not resolved live.

## Open safety/operational questions (not invented source defects)

1. Hostinger/LiteSpeed's actual access-denial behavior and any Nginx proxy bypass need **private-object URL denial tests**. File existence and PHP checks alone do not prove web-server enforcement. Validate the private export location against the actual serving stack before promotion.
2. The active deployed package, DB/schema, migrations, source-to-host checksum, options and runtime logs have not been frozen; a live diagnostic or live bug repair cannot be claimed.
3. File 02/24 and CF04 operational readiness, true File 00 second-factor assertions and restore drills require separate native-owner evidence.
4. The current staging acceptance wizard verifies versioned evidence identifiers but does not independently prove installed-byte checksum parity. An explicit deployment identity/attestation contract must be designed and tested before treating an acceptance record as a live-parity certificate. This is a **review item**, not a claim of an observed live exploit.
5. CI, modeled loads, and static accessibility checks do not replace real-role, 10,000+ object, device/RTL, cross-user cache, backup and rollback tests.
