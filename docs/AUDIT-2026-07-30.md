## Findings and Corrections

### A-001 — Provider-controlled production acceptance — Critical

The original registry trusted `get_maturity_state()` from the provider itself. A provider could return `production_accepted` and satisfy the environment gate without independent File 23 acceptance.

**Correction:** Technical capability and institutional acceptance are separate state domains. Providers declare capability only. Staging/production acceptance is injected by File 23-owned governance and cannot be self-declared through the adapter interface.

### A-002 — Caller-controlled environment bypass — Critical

The original `can_write( provider, is_production )` accepted a caller-supplied Boolean. Production code could pass `false` and use staging acceptance.

**Correction:** The registry resolves `wp_get_environment_type()` server-side. The caller cannot supply or downgrade the environment.

### A-003 — Misleading incomplete authorization method — Critical

The original `can_write()` checked only adapter maturity, despite its name suggesting complete authorization.

**Correction:** It was replaced by `is_environment_write_eligible()`, explicitly documented as only one gate. The guarded operation broker separately enforces registered operation, capability, Membership Core status, object type, version, idempotency, audit reason, reserved authority fields, native authorization, exception isolation, and post-action re-read.

### A-004 — Membership Core fail-open behavior — High

The original capability helper checked only a WordPress capability. It did not verify that File 00 was available or that the current account status allowed the requested authority.

**Correction:** A canonical, versioned Membership Core guard verifies `SMC_VERSION`, `smc_user_status()`, `smc_is_founder()`, and `smc_is_trusted_publisher()`. Mutable and institution-wide capabilities require `approved` or `verified`; compatible File 00 availability is mandatory. Administrators receive a non-sensitive dependency notice when File 00 is missing or incompatible.

### A-005 — Documentation/interface contract mismatch — High

The written contract required provider name/version, supported contract range, privacy classes, capabilities, and operation schemas, but the PHP interface did not require them.

**Correction:** Adapter Contract 2.0.0 requires all governed metadata and operation definitions. Compatibility uses explicit minimum/maximum semantic versions rather than a loose major-number cast.

### A-006 — Silent provider-key normalization and collision risk — High

The original registry passed provider keys through `sanitize_key()`, silently changing them and allowing multiple raw keys to collapse to one canonical key.

**Correction:** Keys must arrive already canonical, bounded, and exact. Lookup no longer silently normalizes untrusted input.

### A-007 — Adapter exception could break registration — High

Provider methods were invoked without exception isolation, contrary to the rule that one adapter failure must not crash the dashboard.

**Correction:** Registration is wrapped in `Throwable` isolation, failures become bounded `WP_Error` records, and a diagnostic registration-error ledger is exposed.

### A-008 — Unregistered operation keys were not executable-code guarded — High

The interface exposed a generic `execute_operation()` method but the registry did not require or validate operation definitions.

**Correction:** Every adapter must declare complete operation definitions. The broker denies any operation absent from that registry snapshot and rejects reserved client-supplied authority fields. The architecture guard prohibits direct adapter mutation calls outside the broker.

### A-009 — Concurrency and replay controls existed only in prose — High

Object version/ETag and idempotency were documented but not enforced by any executable File 23 path.

**Correction:** The broker enforces required object-version, idempotency-key, and audit-reason fields before native execution, then re-reads the native object before reporting confirmed success.

### A-010 — CI coverage was insufficient — High

The original workflow ran syntax checks only on PHP 8.0 plus simple grep rules. It did not test the production PHP 8.3 target, adapter acceptance, Membership Core fail-closed behavior, environment bypass, or operation registration.

**Correction:** CI runs PHP 8.0, 8.1, 8.2, and 8.3; executes contract tests; runs an architectural boundary guard; verifies version/contract alignment; and requires this audit and merge-gate record.

### A-011 — Architectural grep rules were weak — Medium

The original single-line, case-sensitive grep checks could miss multiline table declarations and did not guard direct native post mutations.

**Correction:** An executable PHP architecture guard normalizes content and rejects duplicate native post types, direct native post/attachment mutation, direct posts/comments table access, forbidden native-domain tables, legacy maturity APIs, caller-supplied environment gates, and direct provider mutation outside the operation broker.

### A-012 — Mixed maturity state model — Medium

Technical capability and institutional acceptance were combined into one linear state list, creating ambiguity and provider self-promotion risk.

**Correction:** The model is split into provider-declared technical capability and File 23-controlled acceptance. Effective state is derived fail-closed.

### A-013 — Private/signed destination persistence risk — Medium

The original data contract permitted a stored `canonical_url`, which could accidentally retain expiring signed URLs or private tokens.

**Correction:** File 23 may store only a stable non-secret destination descriptor or canonical public URL descriptor. Signed, nonce-bearing, expiring, credential-bearing, session-bound, or patient-document URLs must be resolved on demand and never persisted.

### A-014 — Review/merge governance was not recorded in repository law — Medium

The project rule prohibiting merge before completed review and defect correction was not yet part of the repository decision log or CI gates.

**Correction:** The rule is added to the Decision Log, Status gates, this audit, and CI verification.

### A-015 — Overbroad account-state denial contradicted the approved plan — High

The first correction denied every File 23 capability to pending and suspended accounts. The governing plan requires a restricted dashboard and read-only/status/appeal route for pending or suspended doctors, while all write actions remain prohibited.

**Correction:** Capability enforcement is divided. Only `spdb_view_dashboard` and `spdb_view_own_content` may pass for a known non-approved File 00 status when those capabilities are actually assigned. Every mutable, review, scheduling, analytics, export, delegation, repair, policy, or institution-wide capability still requires `approved` or `verified`. Executable tests cover submitted and suspended accounts.

### A-016 — File 00 compatibility was detected by symbols but not version — Medium

The first Membership Core guard accepted any plugin defining the expected constant and functions, including an unreviewed major version with changed semantics.

**Correction:** File 23 accepts Membership Core `>= 1.0.1` and `< 2.0.0`. Malformed, older, or unreviewed major versions fail closed. The supplied File 00 package and canonical functions were verified and recorded in Source Provenance. Tests cover the compatibility boundary.

### A-017 — Native object and audit inputs were insufficiently bounded — Medium

The operation broker originally accepted object identifiers with trailing/control characters and did not cap optional audit-reason length.

**Correction:** Native object references reject whitespace mutation, control characters, empty values, and values over 191 bytes. Audit reasons reject control characters and values over 500 bytes. Additional authority-like payload fields, including environment and acceptance state, are reserved.
