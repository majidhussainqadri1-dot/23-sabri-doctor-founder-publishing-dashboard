# فائل ۲۳ — V12.1: نصب شدہ حقیقت کی بےتبدیلی پیمائش اور File20 تصدیقی حوالگی

**تاریخ:** ۱۳ نومبر ۲۰۲۶ء (پاکستان)  
**درجہ:** Source-only operator tooling؛ Hostinger پر عمل **نہیں** کیا گیا؛ نہ یہ WordPress plugin activation ہے، نہ automatic deployed attestation۔  
**حاکم ترتیب:** Live symptom → live evidence → exact deployed version → DB/schema → deployment parity → root cause → repository.

## ۱۔ حقیقی دستاویزی رکاوٹ

File23 Draft PR #29 میں `SPDB_Activation_Wizard`، `spdb/file23_deployed_artifact_attestation` کے مصدقہ source/package/schema/migration ثبوت کے بغیر staging acceptance روک دیتا ہے۔ GitHub Actions کا سبز نتیجہ **Hostinger نصب شدہ build کی حقیقت** ثابت نہیں کرتا۔ معتبر attestor بنانا File20/authorized deployment operator کی ذمہ داری ہے (File20 Issue #45)؛ File23 Issue #30 اسی لیے کھلا ہے۔

۱۳ نومبر کے connector معائنے میں سائٹ `www.sabrihomeopathy.com` کا WordPress.com Jetpack interface **disconnected** تھا اور WPVibe کے تحت کوئی site registered نہ تھی۔ اس سے براہِ راست deploy/DB/Hostinger/HTTP حقیقت کی پڑتال نہیں ہوسکی۔ یہ disconnect **site-down** یا live plugin failure کا ثبوت نہیں۔

## ۲۔ نیا read-only observation helper

`tools/file23-readonly-host-evidence.php` WordPress کو پہلے سے bootstrap کیے ہوئے، **مجاز staging WP-CLI shell** پر صرف موجودہ حالت کی پیمائش کرتا ہے۔ یہ:
- Plugin header/runtime 1.3.0 سمیت اصل observed values اور `wp_get_environment_type()` لیتا ہے؛
- نصب شدہ plugin-tree کی **ہر قابلِ مطالعہ regular file** کے relative name + exact length + SHA-256 کو sort کرکے ایک SHA-256 fingerprint دیتا ہے؛
- symlink، unreadable file، inactive File23 اور header/runtime mismatch کو واضح خطا بتاتا ہے؛
- `spdb_operations_schema_version` اور `spdb_collections_schema_version` کے اصل values اور دونوں `::verify()` نتائج دیتا ہے؛
- source commit، approved ZIP hash، owner identity، transaction/isolation، full migration history اور Hostinger edge access **نہ بناتا ہے، نہ خود تصدیق کا دعویٰ کرتا ہے**؛
- صرف operator CLI JSON پر نتیجہ دیتا ہے؛ Browser/HTTP access سے 404؛ **DB, filesystem, plugin activation, migration, plugin options یا server config میں کوئی تبدیلی نہیں**۔

### مجاز staging پر طریقۂ استعمال

1. Snapshot/backup کے بعد *واقعی فعال plugin* کا نام/مسیر WordPress Plugin UI یا authorized Hostinger shell سے یقینی کریں۔ اگر تنصیب `wp-content/plugins/sabri-publishing-dashboard` کے بجائے کسی اور مقام پر ہے تو probe غیر مصدقہ نتیجہ دے گا؛ اس کا path خاموشی سے نہ بدلا جائے۔
2. GitHub کے **exact accepted commit** سے helper حاصل کرکے host کی کسی محفوظ عارضی، web-root کے باہر فائل میں رکھیں؛ approved operator اس کی SHA بھی پہلے verify کرے۔
3. اصل staging WordPress root سے `wp eval-file /private/operator-path/file23-readonly-host-evidence.php` چلائیں۔ خام JSON کسی عوامی URL، REST response، log یا screenshot میں نہ لگائیں۔
4. رقم شدہ `installed_file_inventory_sha256` کا **اسی algorithm سے** approved installable ZIP extracted tree کے relative-path+byte fingerprint سے مقابلہ کریں۔ یہ checksum GitHub Actions artifact upload ZIP hash کے برابر ہونے کا دعویٰ نہیں؛ دونوں الگ چیزیں ہیں۔
5. `source_commit` اور `package_sha256` کے لیے approved CI manifest اور واقعی deployed package کا chain of custody/byte proof علیحدہ مہیا کریں۔
6. `spdb_operations_schema_version` کی متوقع اصل `1.1.0` اور `spdb_collections_schema_version` کی متوقع اصل `4` کو مطلوبہ tables, columns, indexes اور نامکمل migration state کی **الگ حقیقی** جانچ کے ساتھ ملائیں؛ options alone enough نہیں۔
7. اسی پیمائش کو Live پر **الگ** operator session سے دہرائیں۔ Live/Staging/GitHub کو کبھی ایک ثبوت نہ بنائیں۔ اگر mismatch ہو تو فوری **Deployment-Parity Audit** اور rollout stop۔
8. File20 اپنے آزاد trusted provider، revocation، fresh identity اور File24 assurance کے ذریعے ہی `verified=true` contract جاری کرے۔ File23 کا helper **کبھی بھی** `file23_deployed_artifact_v1` یا activation approval پیدا نہیں کرتا۔
